# Астрономический справочник и RAG — спецификация MVP

**Статус:** исходная спецификация утверждена 14 ноября 2026; самостоятельный репозиторий выделен 17 ноября 2026.

## 1. Цель и границы

Самостоятельный микросервис астрономического справочника. Покрывает **весь** глоссарий Astro4Edu: исходные тексты, русский перевод, связи, медиа и структуру страниц. Отдаёт материалы по API, ищет по базе знаний и отвечает через LLM.

Исходные данные: [глоссарий](https://astro4edu.org/resources/glossary), [API Astro4Edu](https://www.astro4edu.org/oae-api-docs/). На момент составления спецификации API `glossary-terms/?language=en` сообщает 501 запись; при импорте проверяем фактическое число, а не зашиваем 501 в код.

## 2. Что считается материалом

| Тип | Содержимое | Связь |
| --- | --- | --- |
| `term` | Название, алиасы, определение, статус проверки, категории, связи, перенаправление | `term_number` Astro4Edu |
| `term_page` | Разделы страницы термина в исходном порядке, включая связанные медиа и схемы | `term_number` |
| `article` | Развёрнутый текст из доступных материалов Astro4Edu или подготовленный командой и проверенный редактором | Ссылки на термины и исходную страницу |
| `media` / `diagram` | Локальный оригинал и при необходимости локализованная версия, название, подпись, alt-текст, авторство, язык | ID связанных терминов |

Страница глоссария часто содержит то же определение, что API, плюс связанные термины, изображения и схемы с подписями. Она **не автоматически отдельная длинная статья**. Для `article` нужен отдельный развёрнутый материал; его происхождение фиксируется. Отсутствие статьи или изображения представляется пустым списком.

## 3. Зеркало страницы и перевод

Для каждого исходного материала хранить:

- `source`: тип, исходный ID/URL, дата получения, исходный язык, версия/хэш содержимого;
- `metadata`: заголовок, алиасы, категории, уровень проверки, связи, авторство;
- `sections[]`: упорядоченные блоки с `id`, `type`, `heading`, `body`, ссылками и вложенными `media_ids`;
- `locales.en` и `locales.ru`: переводимые поля **с той же структурой и ID блоков**;
- `review`: `draft | reviewed`, дата, редактор, замечания;
- `media[]`: исходный URL, локальные пути к оригиналу/русской версии, SHA-256, подпись и alt-текст на обоих языках, credit, лицензия, ссылка на запись источника.

Неизвестный тип раздела сохранять как исходный блок, а не терять при нормализации. Исходная разметка/JSON остаётся в `data/raw/`; нормализованная запись — в `data/processed/`. **Все изображения** из импортированных материалов скачиваются в `data/media/original/` и обслуживаются с нашего сервера. Подписи и alt-тексты переводятся. Если английский текст нанесён прямо на картинку, ChatGPT создаёт русскую версию в `data/media/ru/`, сохраняя композицию, размер и максимально близкие шрифт, цвет и расположение надписей. Чистые фото без нанесённого текста не перерисовываются.

Для каждой изменённой картинки вести `data/image_edits.json`: ID материала и медиа, исходный/локальный URL, пути оригинала и русской версии, исходные/новые надписи, статус `pending | edited | reviewed`, дату, замечания ревьюера. После каждой партии сообщать в чате список изменённых картинок и ссылки на файлы; ревью перед публикацией обязательно. Словари надписей и локальный OCR-инвентарь хранятся в `data/media/localization/`. Исходный файл никогда не перезаписывать.

Каждая импортированная статья проходит тот же перевод всех разделов, подписей и alt-текстов, что и страница термина. Неполный перевод остаётся черновиком; порядок и типы разделов в `en` и `ru` совпадают.

Пример сокращённой записи:

```json
{
  "id": "term:1",
  "kind": "term_page",
  "source": {
    "term_number": 1,
    "url": "https://astro4edu.org/resources/glossary/term/1/",
    "fetched_at": "2026-11-14T00:00:00Z",
    "raw_snapshots": ["data/raw/terms/1.json", "data/raw/pages/1.html"]
  },
  "metadata": {
    "approval_level": "A",
    "categories": ["Stars"],
    "related_term_numbers": [15, 304]
  },
  "sections": [
    {"id": "definition", "type": "definition", "media_ids": []},
    {"id": "related_media", "type": "media_collection", "media_ids": ["media:example"]}
  ],
  "locales": {
    "en": {"title": "A-type Star", "blocks": {"definition": {"body": "..."}}},
    "ru": {"title": "Звезда спектрального класса A", "blocks": {"definition": {"body": "..."}}}
  },
  "media": [{"id": "media:example", "source_url": "...", "original_path": "data/media/original/example.png", "ru_path": "data/media/ru/example.png", "sha256": "...", "caption_en": "...", "caption_ru": "...", "alt_en": "...", "alt_ru": "...", "credit": "...", "license": "..."}],
  "review": {"status": "draft", "reviewer": null}
}
```

Числа и текст в примере, кроме `term_number: 1` и URL, иллюстративны; импорт берёт реальные значения из источника.

## 4. Импорт, перевод, ревью

1. Забрать все страницы английского API с пагинацией, повтором неудачных запросов и контрольной суммой. Сохранить сырые ответы.
2. Для каждого термина получить структуру страницы; связанные `media` и `diagram` взять из API по `glossary-term=<id>`. Сопоставить с разделами страницы и сохранить порядок. Скачать все изображения и проверить хэши/размеры.
3. Нормализовать термины, перенаправления, связи и материалы. Проверить уникальность ID и отсутствие битых внутренних ссылок.
4. Перевести все текстовые поля на русский пакетами. Локализовать английские надписи внутри изображений через ChatGPT image editing, записать каждую правку в журнал. Сохранять результат каждого пакета; повторный запуск обрабатывает только новые/изменённые поля и не затирает ручные правки.
5. Автопроверка: число записей, паритет блоков `en/ru`, числа и единицы измерения, ссылки, пустые переводы, подписи медиа, наличие локальных файлов и паритет надписей на изменённых изображениях. После неё записи остаются `draft` до редакторского ревью.
6. Ревьюер правит перевод в JSON или через будущий интерфейс; статус `reviewed` выставляется явно. В выдаче клиент видит статус перевода.

Полный охват глоссария обязателен. Развёрнутые статьи добавляются для всех тем по мере наличия проверенного материала; сервис работает и с терминами, для которых такой статьи пока нет.

После оценки PR #2 корпус пополняется двуязычными статьями об эффекте Доплера и геостационарной орбите. Статьи с библиографией хранятся в `data/processed/articles/` со статусом `draft` до редакторского утверждения. Оценка статей отдельно проверяет выбор материала и ссылки на его разделы на обоих языках.

## 5. Хранилище, чанкинг и индекс знаний

- **Канонические данные:** версионируемые JSON в `data/processed/`; исходные снимки в `data/raw/`; оригиналы и русские изображения в `data/media/`. Рабочая БД хранит локальные пути и метаданные файлов.
- **Рабочая БД:** SQLite. При запуске/импорте загружает записи, связи и медиа; FTS5 индексирует русский и английский текст. БД можно полностью восстановить из JSON.
- **RAG-индекс:** поиск совмещает FTS5 и многоязычные эмбеддинги. Векторный индекс FAISS `IndexFlatIP` с нормализованными векторами даёт точный cosine-поиск без отдельного сервера. Каждый чанк содержит `record_id`, `section_id`, язык, локальный URL, заголовок, тип материала, статус ревью и указатель на исходный блок.
- Изменение перевода перестраивает только затронутые чанки. Пустые/перенаправляющие записи не превращаются в фиктивный текст.

**Чанкинг:**

1. Сначала разобрать страницу в дерево разделов. Определение термина — отдельный цельный чанк; подпись изображения/схемы — отдельный чанк, связанный с изображением и термином; статью делить по заголовкам, абзацам и смысловым переходам.
2. Не разрывать формулы, таблицы, списки с пояснениями и единицы измерения. Не смешивать разные статьи или языки в одном чанке. При длинном разделе делить по абзацам с малым перекрытием только внутри раздела.
3. Вставлять в текст для поиска хлебные крошки: название материала → заголовки разделов. Хранить точный текст отдельно от поискового текста, чтобы не показывать пользователю искусственные повторы.
4. Размер чанка подбирать по контрольному набору вопросов, а не по одной константе: сравнить ориентиры 250/400/600 токенов и перекрытие 0–15%. Проверять `Recall@k`, `MRR`, точность ссылки на статью/термин и верность ответа источникам. Утвердить конфиг по результатам.
5. Для каждого чанка хранить стабильный ID и хэш содержимого. Изменение перевода пересчитывает только изменённые эмбеддинги; публикация нового индекса атомарна.

**Runpod:** после локального чанкинга выгружать `chunks.jsonl` на временный GPU Pod. Там пакетно считать многоязычные эмбеддинги и собирать индекс. Вернуть `index.faiss`, таблицу соответствия `vector_id → chunk_id` и `index-manifest.json` с моделью/версией эмбеддингов, конфигом чанкинга, числом чанков, размерностью и хэшами. Локальный сервис проверяет манифест и загружает готовый индекс на CPU; Runpod не нужен для каждого запроса. После выгрузки артефактов Pod останавливается. Полный пересчёт повторяем на Runpod; мелкие изменения допускают пакетный инкрементальный пересчёт тем же пайплайном.

## 6. Ассистент LLM

Запрос: `question`, `mode: auto | term | article | explain | general`, `locale: ru | en`, необязательный `context` (например, ID открытого термина).

По умолчанию используется DeepSeek; `ASSISTANT_PROVIDER=runpod` и `RUNPOD_ENDPOINT_ID` позволяют выбрать RunPod. Ключи остаются только на сервере. В `auto` сервер находит кандидатов во **всём** справочнике и материалах, затем модель выбирает форму ответа; это основной путь. Явный `mode` остаётся опцией API для клиентов и отладки:

| Режим | Когда | Результат |
| --- | --- | --- |
| `term` | Прямой вопрос «что такое X?» | Короткое определение + ссылка на термин |
| `article` | Пользователь просит разобраться в теме, есть подходящая статья | Краткое введение + ссылка на конкретную статью |
| `explain` | Нужны сравнение, причины, несколько источников | Развёрнутый ответ + ссылки на использованные блоки |
| `general` | Астрономический вопрос, для которого нет подходящего материала | Ответ модели от себя, `grounding: model`, без выдуманных ссылок |

Модель за один вызов определяет область вопроса и фактический режим, выбирает ID доказательств и при необходимости пишет ответ. При `term` сервер отдаёт полный канонический блок определения без перефразирования. При `article` требуется хотя бы один подтверждённый фрагмент статьи. Запрос с явным `mode: article` при отсутствии использованной статьи может вернуть `explain` с покрытием `partial` или `insufficient`. Для остальных явно указанных режимов несовместимый результат модели считается недостаточным. Посторонний запрос возвращает фиксированный `out_of_scope` на языке запроса независимо от выбранного режима.

В prompt передаётся максимум шесть фрагментов, каждый с коротким ID. Текст запроса и материалов — данные. Ответ модели валидируется строгой схемой. Сервер принимает только фрагменты из переданного набора, отбрасывает блоки с неподтверждёнными ID и формирует URL из каталога. Фактический режим и поля `answer`, `grounding`, `primary_url`, `review_status`, `sources`, `images` сохраняют формат. Дополнительно `coverage` обозначает `complete | partial | insufficient`, а `blocks[].source_indices` ссылается на нулевые индексы массива `sources`. Источник содержит ID записи, раздела, URL и опциональный `chunk_id` целиком использованного индексного фрагмента. Для подписи `section_id` — ID медиа записи, URL ведёт к метаданным медиа, а при наличии файла показывается само изображение. При частичной выдаче сервер добавляет сообщение о пробеле.

Основная оценка вызывает тот же путь `answer()` по полному набору RU/EN. Проверяются финальный режим, политика источников, точные разделы, обязательные и запрещённые факты, частичный/недостаточный ответ, время и токены. Прогон без LLM проверяет все группы источников, включая требования отдельных фактов, и учитывает явно заданный режим запроса. Лексические проверки фактов служат воспроизводимым регрессом, научную полноту дополнительно проверяют по рубрике. Отчёт указывает провайдера, модель, версию промпта, p50/p95 и стоимость на валидный ответ при задании тарифа.

Новые статьи проверяет `python -m scripts.evaluate --suite data/eval/assistant/article_questions.json`. В основном наборе ответ при отсутствии отдельной статьи проверяется на годичном параллаксе.

## 7. HTTP API

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| GET | `/health` | Готовность процесса; работает без ключа LLM |
| GET | `/api/v1/terms` | Пагинация, поиск, фильтры по категории/букве/статусу |
| GET | `/api/v1/terms/facets` | Буквы и категории с числом терминов |
| GET | `/api/v1/terms/{term_number}` | Полная двуязычная запись термина, связанные материалы |
| GET | `/api/v1/terms/{term_number}/illustration` | Локальная иллюстрация термина |
| GET | `/api/v1/articles` | Список и поиск развёрнутых материалов |
| GET | `/api/v1/articles/{article_id}` | Полная статья с переводом и медиа |
| GET | `/api/v1/media/{media_id}` | Метаданные и подписи изображения/схемы |
| GET | `/api/v1/media/{media_id}/file` | Локальный файл в выбранном языке (`locale=ru|en`) |
| GET | `/api/v1/search` | Единый поиск по терминам, статьям и подписям |
| POST | `/api/v1/assistant/answer` | Выбор режима, RAG, вызов LLM, источники и изображения |

Списки возвращают `items`, `total`, `page`, `page_size`. За пределами выдачи `items` пуст. Номер термина вне диапазона знакового 64-битного целого даёт `422 validation_error`. По умолчанию выдаётся русский текст, а оригинал доступен в полной записи. Ошибки имеют `code`, `message`, `details`; ответ `405` содержит `Allow`; отсутствие ключа LLM даёт `503 assistant_unavailable`, чтение материалов продолжает работать. OpenAPI генерируется FastAPI из моделей запроса/ответа; `/docs` (Swagger UI) и `/openapi.json` обязательны, с примерами всех режимов и ошибок.

**Rate limit:** для `POST /assistant/answer` — 1 запрос на клиента за 10 секунд; при раннем повторе `429 rate_limited`, заголовок `Retry-After` показывает остаток ожидания (максимум 10 секунд). Для чтения/поиска — 30 запросов за 10 секунд, для файлов медиа — 120 за 10 секунд; превышение запускает 10-секундный cooldown без продления от отклонённых запросов. Лимит клиента считать по подписанной сессии; если её нет — по доверенному IP от настроенного reverse proxy. Дополнительный общий лимит по IP не даёт обходить ограничение созданием новых сессий; произвольным `X-Forwarded-For` клиента не доверять. Счётчики — в Redis, общие для всех экземпляров. Дополнительно ограничить длину вопроса/тело запроса, таймаут LLM и число одновременных вызовов; при отсутствии свободного слота возвращать `503` с `Retry-After: 10`. На `/health` внутренний probe не тратит пользовательский лимит.

Пример ответа помощника:

```json
{
  "mode": "article",
  "grounding": "knowledge_base",
  "answer": "...",
  "primary_url": "/api/v1/articles/article:spectral-types",
  "sources": [{"record_id": "article:spectral-types", "section_id": "overview", "url": "/api/v1/articles/article:spectral-types", "review_status": "reviewed"}]
}
```

URL в примере иллюстративный. Фронтенд решает, показать карточку термина, превью статьи или полный ответ.

## 8. Docker и конфигурация

Сервис запускается через FastAPI, Dockerfile и Compose. `docker compose up --build` поднимает сервис на `127.0.0.1:8001`, внутри контейнера порт `8000`. Снимки, переводы, медиа и индекс лежат в примонтированной `data/`. Рабочая SQLite в Compose хранится в отдельном volume, путь задаёт `CATALOG_DB_PATH`. При локальном запуске путь по умолчанию — `data/glossary.db` внутри выбранного `DATA_DIR`. Compose передаёт перечисленные в `compose.yaml` настройки из окружения или `.env`, запускает Redis для лимитов и задаёт внутренние адреса Redis и сервера эмбеддингов. Остальные значения по умолчанию задаёт приложение. Пустой ключ допустим для `/health`, чтения материалов и поиска. Эмбеддинги для индекса можно считать пакетно на RunPod. Для гибридного поиска нужен сервер эмбеддингов из профиля `embeddings` или по адресу `EMBEDDING_URL`.

В первом релизе импорт/перевод/переиндексация запускаются отдельными командами внутри контейнера, а не пользовательскими HTTP-запросами. Публичный API доступен только на чтение, кроме запроса к ассистенту.

Базовые тесты каркаса: `python3 -m pip install -r requirements-dev.txt`, затем `python3 -m unittest discover -s tests -v`. По мере реализации маршрутов добавить контрактные тесты с подменой DeepSeek/Runpod, проверки лимита на управляемых часах и тест целостности локальных медиа.

## 9. Критерии готовности

- Импортированы все записи из текущего API; есть оригинал и русский черновик каждого непустого поля; структура страницы и связи сохранены.
- Для медиа и схем сохранены оригинальные и русские подписи/alt-тексты; отсутствующие элементы честно пусты.
- Все исходные изображения скачаны и доступны с нашего API. Все изображения с английским текстом внутри имеют русскую версию и запись в `data/image_edits.json`; результаты показаны на ревью.
- Повторный импорт не создаёт дубликаты и не стирает редакторские исправления.
- Чанки сохраняют смысловые границы; выбор размера подтверждён контрольными вопросами. Индекс и манифест собраны на Runpod, повторно загружаются сервисом без GPU.
- Поиск отвечает на русские и английские запросы по всему словарю, возвращает точные URL.
- Ассистент различает короткий термин, статью, составное объяснение и общий ответ; не ссылается на несуществующие записи.
- Базовые автотесты покрывают `/health`, `/docs`, `/openapi.json`, выдачу материалов и медиа, поиск, целостность данных, ограничения запросов, четыре режима ассистента и ошибки DeepSeek. Внешние API подменяются; отдельно — smoke-тест Docker.
- `docker compose up --build` запускает сервис; `/health` и `/docs` доступны; без ключа DeepSeek справочник и поиск продолжают работать.

## 10. Порядок реализации

Полный импорт и зеркало страниц/изображений → перевод всех полей и локализация изображений → ревью → чанкинг и оценка качества → Runpod: эмбеддинги/индекс → БД/поиск/RAG → DeepSeek и промпты → тесты → интеграция с фронтендом. На момент утверждения создан только запускаемый каркас.

## 11. Дополнения к контракту (14 ноября 2026)

**Переводы при повторном импорте.** Если английский текст поля изменился, русский перевод больше не стирается без следа: прежний текст сохраняется в `stale_translations[] = {path, previous_en, previous_ru, detected_at}`, поле очищается для нового перевода, запись получает `draft` с пометкой. Новый раздел или изменённая подпись медиа тоже сбрасывают статус проверки. Импорт оригиналов изображений сверяет скачанный файл с записанным SHA-256 и при расхождении не принимает его.

**Повторное получение источника.** `--refresh` сохраняет новую версию API/HTML в `data/raw/` под хэшем содержимого; прежние снимки не перезаписываются. Указатель `.current` выбирает последнюю версию, а `source.raw_snapshots` фиксирует пути выбранных снимков. Добавление, удаление или изменение раздела/медиа возвращает запись в `draft`; переводы удалённых полей остаются в `stale_translations`. Изменённый оригинал изображения сохраняется новым файлом; прежняя русская версия перестаёт выдаваться до повторной локализации.

**Выбор контекста ассистента.** Каноническое определение и найденный доказательный фрагмент живут отдельно. Для объяснения предпочтение получают определения, релевантные разделы статей и фактические подписи. Индексный текст используется, только когда он соответствует текущему разделу. Навигация и учебные активности не замещают определения. Статьи — самостоятельные двуязычные материалы с библиографией и статусом редакции.

**Размер запроса помощнику.** `Content-Length` проверяется как ранний фильтр: некорректное значение даёт `400`, превышение 16 КиБ — `413`. Независимо от заголовка тело читается с пределом 16 КиБ; превышение также даёт `413`. Прочитанное тело передаётся обработчику без повторного чтения из сети.

**Поиск.** FTS5 индексирует нормализованный текст (`casefold`, `ё → е`) и основы слов (Snowball, русский и английский); служебные слова запроса отбрасываются. Векторный поиск необязателен: если индекс, модель или сервер эмбеддингов недоступны, выдача лексическая и ответ содержит `mode: "lexical"`. Семантические соседи ниже косинуса 0,55 не считаются совпадением (калибровка на контрольных запросах). `total` — пул релевантных результатов, не больше 200.

**Рабочая БД.** SQLite хранит отпечаток набора канонических JSON (имена, размеры, время изменения) и версию схемы. При запуске и не чаще раза в 30 секунд сервис сверяет отпечаток и пересобирает БД атомарной заменой файла. Сборка без канонических терминов завершается ошибкой. При ошибке пересборки чтение продолжает работать из последней БД совместимой версии с терминами, следующая автоматическая попытка происходит через 30 секунд. Если рабочей БД ещё нет, ошибка сборки завершает запуск.

**Обложки терминов.** Отдельно от исходных медиа Astro4Edu: файлы `data/media/illustrations/<term_number>.webp`, манифест `data/illustrations/manifest.json` — по одному элементу на каждый из 501 термина. Приоритет — свободное изображение Wikimedia Commons, связанное со статьёй Wikipedia по теме термина; если его нет или оно содержит английские надписи, допустимо уже импортированное лицензированное медиа Astro4Edu. Для абстрактных понятий допускается явно записанная привязка к изображению близкого термина с подписью «Связанное изображение». Файлы прямого отбора и связанных замен хранятся в `data/illustrations/selection/`. Для каждого файла сохраняются URL страницы файла, автор, лицензия, URL лицензии, источник, размер и SHA-256. OCR отсеивает явные латинские надписи; статус `generated` означает технический импорт, `approved` — редакторское подтверждение содержания. API отдаёт только `generated` и `approved`: в записи термина — объект `illustration` с атрибуцией, файл — `GET /api/v1/terms/{number}/illustration`. Подбор и импорт изображений из источников выполняет `scripts/wikimedia_covers.py`; контроль полного покрытия — `python -m scripts.illustrations verify --complete`.

**Ревью переводов.** `scripts/translation_audit.py` проверяет каждое непустое переводимое поле всех записей: собирает уникальные пары EN/RU, отдаёт их рецензенту в контексте термина, каждое предложенное исправление проверяет независимая модель, применяет только подтверждённые и прошедшие детерминированные проверки (числа и единицы, длина, переносы строк, URL). Ручные правки редактора автоматически не переписываются, откат прежних исправлений запрещён. Статусы `review` записей не меняются: автоматическое ревью — не подтверждение человеком. Отчёт по каждому ID — `data/eval/translation_audit/report.json`, сводка — `summary.md`, журнал применённых и спорных правок — `applied.json`.

## Самостоятельный сервис

FastAPI обслуживает только справочник, поиск, медиа и помощника. Публичный API доступен по путям `/api/v1/*`; `/health`, `/docs` и `/openapi.json` доступны напрямую.
